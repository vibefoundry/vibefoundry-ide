# Publish — instructions for an LLM

This is a **drop-in packaging folder**. Put it in the root of any VibeFoundry app
(next to `backend/`, `frontend/`, `data/`) and it turns that app into a
**self-contained desktop app** with a one-click installer for macOS + Windows.
`publish.py` refers to the app's files one level up (`../backend`, `../frontend`,
`../data`), so it works in any app root — no edits needed for the path wiring.

Read this whole file before editing anything here. Most app changes need **no**
edits to `publish.py` — see "When the app changes".

---

## Files in this folder
- `publish.py` — the packager (run this).
- `vf_logo.png` — branding (app icon, splash, favicon). **Replace this file to rebrand.**
- `README.md` — this file.

This folder is portable: it lives at `<template>/Publish/` and refers to the
template's own files one level up. Copy the whole folder into another template to
reuse it.

---

## How to run
From the template root:
```
python Publish/publish.py "My App Name"
```
- The app name comes from the user (CLI arg; prompts if omitted). It drives the
  install-folder slug, the Desktop launcher label, and the window title.
- Output: `Publish/published_apps/<slug>_v{N}/` containing `install.command`,
  `install.bat`, and `application_core/` (the shipped app). This output is
  gitignored (it's large) so it isn't committed/deployed with the template.
- The end user runs the installer once. It installs into
  `~/Documents/VibeFoundryApplications/<slug>/` (mac) or
  `%USERPROFILE%\Documents\VibeFoundryApplications\<slug>\` (windows), fully
  self-contained there, and drops a branded Desktop launcher. Uninstall = delete
  that folder + the Desktop icon.

Run env needs: Python 3, Node/npm, and internet (it builds the frontend and
downloads dependency wheels). macOS target is **Apple Silicon only**.

---

## What `publish.py` does (pipeline)
1. **Build frontend** — `npm ci` + `vite build` → static files Flask serves
   same-origin. Also drops the favicon + PWA manifest + a service worker.
2. **Vendor wheels** — `pip download` of `../backend/requirements.txt` for BOTH
   `win_amd64` and `macosx_arm64`, so the install is offline + version-pinned.
3. **Assemble** `application_core/` — backend, built frontend, data, wheels, icons.
4. **Icons** — `vf_logo.png` → `.ico` (Pillow) + `.icns` (iconutil), padded square.
5. **Emit installers + launchers** — a loading-bar installer, a Terminal/console
   launcher that runs the server in the foreground + opens a branded app-mode
   browser window via a splash screen.

The end-user runtime is **one Flask process** serving the built frontend AND the
API on one port. Node is only needed at *install* time (for codex); not at runtime.

---

## THE CONTRACT (what the app must provide — keep these intact)
`publish.py` makes a few assumptions about the app. If a vibe coder rewrites the
app, **these must survive** or the published app installs but won't run right.

In `../backend/app.py`:
- **Serves the built frontend** — a catch-all route returns `frontend_dist/`
  files (and `index.html` for unmatched paths), while `/api/*` routes still work.
- **`GET /api/health`** — returns 200 when up (the splash polls this to know when
  to show the app).
- **`POST /api/heartbeat`** — the frontend pings it; a watchdog thread self-exits
  the server if no heartbeat arrives within a grace window (so closing the last
  window cleans up the process). Only active when `VF_PUBLISHED=1`.
- **Reads `BACKEND_PORT`** from the env (the launcher picks the port) and binds it.

In `../frontend`:
- A **Vite** app that builds to `dist/`.
- Calls the backend with **relative `/api/...`** URLs (so same-origin serving works
  — no hardcoded `http://localhost:PORT`).
- Sends the **heartbeat** to `/api/heartbeat` on a timer.

In `../backend/requirements.txt`:
- **Every** Python dependency the app imports (publish vendors exactly this list).

If all of the above hold, adding features/endpoints/UI/data needs **zero** changes
in this folder.

## Reference: the exact edits that make an app publish-ready

> **Assistant: if the app appears to be a chatbot application** (a Flask backend
> + a Vite chat UI, like the codex chatbot), **apply all of the edits below** to
> make it publish-ready before running `publish.py`. They're the standard set for
> that kind of app and are safe (no-ops in dev).

These are the precise changes that turn a standard Flask + Vite app (the codex
chatbot) into a publishable one — **7 edits across 3 files**. Everything else
(installers, launchers, splash, `manifest.webmanifest`, `sw.js`, icons) is
generated by `publish.py`; only these live in the app. All are **no-ops in dev**
(`VF_PUBLISHED` unset, `frontend_dist` absent, `/api/heartbeat` just 204s).

**`backend/app.py`**

1. Import `send_from_directory`:
   ```python
   from flask import Flask, Response, jsonify, request, send_file, send_from_directory
   ```
2. Serve the built frontend so ONE Flask process serves UI + `/api` on one port:
   ```python
   FRONTEND_DIST = APP_DIR / "frontend_dist"

   @app.route("/", defaults={"path": ""})
   @app.route("/<path:path>")
   def serve_frontend(path):
       if path.startswith("api/"): return jsonify({"error": "not found"}), 404
       if not FRONTEND_DIST.exists(): return jsonify({"error": "frontend not built"}), 404
       cand = FRONTEND_DIST / path
       if path and cand.is_file(): return send_from_directory(FRONTEND_DIST, path)
       return send_from_directory(FRONTEND_DIST, "index.html")   # SPA fallback
   ```
3. Published-mode lifecycle (heartbeat + watchdog + portfile), gated on `VF_PUBLISHED=1`:
   ```python
   _PUBLISHED = os.environ.get("VF_PUBLISHED") == "1"
   _HEARTBEAT_GRACE_SECONDS = int(os.environ.get("VF_HEARTBEAT_GRACE", "90"))
   _PORTFILE = APP_DIR / ".server_port"
   _last_heartbeat = time.time(); _heartbeat_lock = threading.Lock()

   @app.route("/api/heartbeat", methods=["POST"])
   def heartbeat():
       global _last_heartbeat
       with _heartbeat_lock: _last_heartbeat = time.time()
       return ("", 204)

   def _watchdog():
       while True:
           time.sleep(5)
           with _heartbeat_lock: idle = time.time() - _last_heartbeat
           if idle > _HEARTBEAT_GRACE_SECONDS:
               try: _PORTFILE.unlink(missing_ok=True)
               except OSError: pass
               os._exit(0)
   ```
   ...and in `__main__`, after the port is chosen (the app must already read
   `BACKEND_PORT` from the env when binding — the codex chatbot already did):
   ```python
   if _PUBLISHED:
       import atexit
       try: _PORTFILE.write_text(str(port), encoding="utf-8")
       except OSError: pass
       atexit.register(lambda: _PORTFILE.unlink(missing_ok=True))
       threading.Thread(target=_watchdog, daemon=True).start()
   ```
4. **Agent CLI full-path fix** — resolve `shutil.which("codex")` and pass the path
   (not the bare name) in EVERY codex subprocess, including the login endpoint.
   See "If your app drives an agent CLI" below for the full detail.

**`frontend/index.html`** (PWA + branding)

5. In `<head>`:
   ```html
   <link rel="icon" type="image/png" href="/vf_logo.png" />
   <link rel="manifest" href="/manifest.webmanifest" />
   <meta name="theme-color" content="#0f1115" />
   ```
6. Register a service worker before `</body>`:
   ```html
   <script>
     if ('serviceWorker' in navigator)
       window.addEventListener('load', () => navigator.serviceWorker.register('/sw.js').catch(()=>{}))
   </script>
   ```

**`frontend/src/App.jsx`** (pairs with #3 — sends the heartbeat)

7. ```jsx
   useEffect(() => {
     const ping = () => { fetch('/api/heartbeat', { method: 'POST' }).catch(() => {}) }
     ping(); const id = setInterval(ping, 15000)
     const onVisible = () => { if (document.visibilityState === 'visible') ping() }
     document.addEventListener('visibilitychange', onVisible)
     return () => { clearInterval(id); document.removeEventListener('visibilitychange', onVisible) }
   }, [])
   ```

**Not changed:** `prompt.py` (already resolves the codex path), `requirements.txt`,
and the dev launchers (`run_app.sh` / `setup.sh`).

## If your app drives an agent CLI (codex / Claude Code / Gemini)

Apps that shell out to a local agent CLI (e.g. the backend runs `codex exec`) have
extra **app-level requirements** that aren't about packaging — but if they're
missing, the *published* app breaks (especially on Windows). When verifying an app,
the assistant should ensure ALL of these in the backend. These are the exact fixes
that were needed to get a codex app working as a published desktop app:

1. **Resolve the CLI's full path — never pass the bare name.**
   `subprocess.run(["codex", ...])` fails on Windows with **WinError 2**: `CreateProcess`
   doesn't do PATH+PATHEXT lookup for a bare name, and the CLI is really a `.cmd` shim.
   Resolve it once and pass the result:
   ```python
   import shutil, subprocess
   codex_path = shutil.which("codex")          # -> ...\codex.cmd on Windows
   if not codex_path: ...                        # surface a clear "not installed" error
   subprocess.run([codex_path, "exec", ...])     # NOT ["codex", ...]
   ```
   Apply this to **every** place the CLI is invoked — codegen, the `/api/auth/.../login`
   endpoint, and any status check. (A common bug: the codegen call gets fixed but the
   login endpoint still passes the bare name and fails on first sign-in.)

2. **Force UTF-8 on the subprocess.** Pass `encoding="utf-8"` to `subprocess.run`
   (and write any stdin as UTF-8). Windows defaults to cp1252 and throws on non-ASCII
   in prompts or output.

3. **Read the CLI's home dir from the env — don't hardcode `~/.codex`.** The launcher
   this tool emits sets `CODEX_HOME` to a folder *inside the app* (`codex_home/`) and
   creates it. The backend must honor that env var so auth stays contained and portable.

4. **Recover from "not logged in" with a login flow, not a crash.** When the CLI has no
   auth, detect the failure and return an error the frontend turns into a "Sign in"
   modal (the codex template's `CodexAuthModal` + `POST /api/auth/codex/login`, which runs
   `codex login` → browser OAuth). The login subprocess needs the **same full-path fix as #1**.

5. **Don't run a blocking login-status pre-flight at startup.** On some Windows machines
   `codex login status` hangs forever. Check auth **lazily** (on first real call) and
   recover via the login flow above, rather than gating app startup on it.

If the app uses a different agent (Claude Code, Gemini CLI), the same five points apply —
just swap the binary name and its home-dir env var.

## When the app changes — what (if anything) to edit
| The vibe coder… | Edit |
|---|---|
| Adds/removes a **Python** dependency | `../backend/requirements.txt` only |
| Adds/removes an **npm** dependency | `../frontend/package.json` (+ lockfile) only |
| Adds endpoints / UI / logic / data | **nothing** |
| Needs a different **Python version** | `TARGET_PY` (and `TARGET_PY_TAG`) near the top of `publish.py` |
| Targets **Intel Mac / Linux** too | `PLATFORMS` in `publish.py` (add platform + its wheels) |
| **Drops codex** / switches LLM (e.g. OpenAI/Claude API) | Remove the "Installing Codex CLI" step from `INSTALL_COMMAND` and `INSTALL_BAT` in `publish.py` |
| Adds a **different external CLI tool** | Add an install step alongside the codex one |
| **Renames the backend entry** (not `backend/app.py`) | The `python backend/app.py` line in `RUN_APP_COMMAND` / `RUN_APP_BAT` |
| Needs **two processes / a non-Flask server** | The launcher model (it starts one Flask process) |

**Wheel caveat:** every dependency must have a **prebuilt wheel** for the target
platforms. A dep that only ships source (no `win_amd64` / `macosx_arm64` wheel)
makes the vendoring step (`pip download --only-binary=:all:`) fail. Prefer
wheel-shipping deps, or add a source-build fallback.

## Dropping `Publish/` into another template
1. Copy this whole `Publish/` folder into the other template's root (next to its
   `backend/`, `frontend/`, `data/`).
2. Make sure that template's app honors **THE CONTRACT** above. If its `app.py`
   lacks the frontend-serving route, `/api/health`, `/api/heartbeat`, the watchdog,
   or `BACKEND_PORT` handling, **add them** (copy the patterns from this template's
   `../backend/app.py`).
3. Adjust `publish.py` assumptions only if the new app differs: external tools
   (does it use codex?), `TARGET_PY`, `PLATFORMS`, backend entry point.
4. Replace `vf_logo.png` to rebrand.
5. Run `python Publish/publish.py "App Name"`.

## Assumptions & limitations (the edges)
- **macOS = Apple Silicon (arm64)** only.
- **Install path must be space-free** — that's why the install folder is
  `VibeFoundryApplications/<slug>` (no spaces): the Miniforge installer refuses
  any install prefix containing a space, on every OS.
- **codex-specific:** the installer runs `npm install -g @openai/codex`, and each
  end user authenticates their own codex on first use (browser OAuth via the app's
  re-auth modal). Remove this if the app doesn't use codex.
- **Per-app runtime, ~1.6 GB** — each installed app carries its own Miniforge +
  env (nothing shared between apps). That's the deliberate "fully contained" trade.
- The installer hides all output behind a progress bar and writes the full log to
  a temp file; on failure it prints "Installation Failed, here's why:" + the log.
